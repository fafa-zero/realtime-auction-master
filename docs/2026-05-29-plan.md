# 2026-05-29 开发计划

## 当前状态

截至 2026-05-28，项目已经跑通基础演示闭环：

- Web 主播端可以开始竞拍、出价演示、封顶成交、模拟支付。
- 微信小程序可以登录、进入专场、自动刷新竞拍状态、参与出价、查看订单。
- 后端已经支持直播间、竞拍、出价、订单、支付状态和本地数据持久化。
- 本地稳定演示入口统一为 `http://localhost:4300/host?liveRoomId=live-1` 和微信开发者工具里的 `apps/miniprogram`。

5 月 29 日的目标不是继续修零散问题，而是把项目从“竞拍 Demo”升级为“商家可配置商品、买家可登录参与、AI 辅助讲解”的产品雏形。

## 5 月 29 日核心目标

1. 增加 Web 登录界面，区分商家/主播进入控制台。
2. 增加微信小程序登录界面，让买家主动登录后再进入专场。
3. 增加商家商品导入能力，优先支持固定模板 Excel。
4. 后端根据导入商品自动生成竞拍配置。
5. 商家端可以看到待竞拍商品队列，并选择某个商品开始竞拍。
6. AI 根据商品信息生成讲解文案，并在 Web 主播端和小程序商品详情中展示。

## 推荐实现顺序

### 1. 登录入口

先做演示登录，不要接真实账号体系。

Web 端：

- 新增登录页。
- 默认提供两个角色入口：
  - 商家/主播：进入商品导入和竞拍控制台。
  - 买家预览：进入 Web 观众页。
- 登录后把用户信息存在前端状态或 `localStorage`。
- 后端先用演示 token，不做复杂权限系统。

小程序端：

- 新增登录页或登录卡片。
- 买家点击“进入好物专场”后调用现有小程序登录接口。
- 登录成功后进入直播间列表。
- 如果 token 失效，回到登录页或重新演示登录。

账号持久化规则：

- 注册和登录必须分清楚：注册只创建新账号，登录只查已有账号并发 token。
- Web 端账号用 `username`、`phone` 或 `email` 作为唯一字段；重复注册时返回“账号已存在，请直接登录”。
- Web 登录时根据唯一字段查用户，校验密码或演示口令，通过后返回 token，不创建新用户。
- 小程序端真实上线时用 `wx.login()` 换取 `openid`，后端用 `openid` 查用户；存在就直接登录，不存在才创建。
- 演示阶段如果不接真实微信，继续用稳定 `mockCode/openId` 作为小程序唯一身份，不要每次进入都生成新用户。
- 用户账号必须写入持久化数据文件或数据库，token 可以过期，但账号不能随着 token 过期消失。
- `GET /api/me` 用于验证 token 并返回当前用户，前端启动时先查 `me`，查不到再回到登录页。

建议 commit：

```text
frontend: add demo login entry
miniprogram: add buyer login screen
server: add demo role login
```

### 2. 商品导入和竞拍配置

先支持一种固定模板，避免做复杂通用表格系统。

Excel 模板字段建议：

```text
商品名称
商品描述
起拍价
最低加价
封顶价
竞拍时长秒
商品卖点
讲解关键词
```

后端能力：

- 新增上传接口。
- 解析 Excel。
- 校验价格字段必须是数字。
- 每行生成一个商品和一个待开始竞拍配置。
- 返回导入结果：成功数量、失败行、错误原因。

Web 商家端：

- 上传 Excel。
- 展示导入预览。
- 展示商品队列：待竞拍、竞拍中、已成交、已结束。

建议 commit：

```text
server: import auction products from spreadsheet
frontend: add product import queue
```

### 3. 自动竞拍队列

目标是让商家上传后可以按顺序竞拍，不需要每次手动填价格。

功能范围：

- 点击“开始竞拍”时使用商品自带的起拍价、加价幅度、封顶价、竞拍时长。
- 竞拍成交或流拍后，商品状态更新。
- 提供“开始下一件”按钮。
- 小程序自动刷新后看到当前正在竞拍的商品。

先不要做完全无人值守自动开始，避免演示时节奏不可控。优先做“半自动队列”：商家确认后开始下一件。

建议 commit：

```text
server: support product auction queue
frontend: add next product auction controls
miniprogram: show queued auction product state
```

### 4. AI 讲解文案

目标是让 AI 能明显提升项目亮点。

后端：

- 根据商品名称、描述、卖点、价格规则生成讲解词。
- 保存到商品字段，例如 `aiScript`。
- 没有模型 API Key 时继续使用本地兜底文案，保证演示稳定。

Web 商家端：

- 商品详情显示完整 AI 讲解词。
- 支持“重新生成讲解词”。

小程序端：

- 商品详情显示精简讲解文案。
- 可以用标题“AI 好物讲解”。
- 不需要显示太长，控制在 3-5 行，避免页面拥挤。

建议 commit：

```text
server: generate product auction scripts
frontend: show ai product scripts
miniprogram: show ai product script
```

## 提前完成后的升级方向

如果上述内容提前完成，可以继续做这些增强，按优先级排序：

### P1：演示效果增强

  - 主播讲解词。

### P4：最终展示增强

## Git 规则

严格保持小步提交，不要一天结束后一次性提交全部内容。

### 基本规则

- 一个小功能一个 commit。
- 只 `git add` 本次相关文件。
- 不要把无关修改、临时文件、构建缓存混入提交。
- 提交前先看状态：

```bash
git --git-dir=.gitdata-local --work-tree=. status --short
```

本项目当前 Git 元数据使用 `.gitdata-local`，所以如果普通 `git status` 不可用，统一使用：

```bash
git --git-dir=.gitdata-local --work-tree=. <git-command>
```

### 提交前检查

每个功能提交前至少运行：

```bash
npm --workspaces run typecheck
```

涉及 Web 页面或构建时运行：

```bash
npm --workspace apps/web run build
```

涉及小程序 JS 时至少运行：

```bash
node --check apps/miniprogram/app.js
node --check apps/miniprogram/utils/api.js
node --check apps/miniprogram/pages/index/index.js
node --check apps/miniprogram/pages/live/index.js
node --check apps/miniprogram/pages/orders/index.js
```
